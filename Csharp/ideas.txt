**Rust features useful in C# fall into two categories: (1) idiomatic patterns and mindsets you can adopt directly in C#, and (2) actual interop so you can call high-performance/safe Rust code from C#.**

### 1. Patterns and Mindsets You Can Apply in Pure C#

These are the most immediately practical.

#### Explicit Error Handling with `Result<T, E>` (instead of exceptions or null)
Rust’s `Result<T, E>` and `Option<T>` make success/failure and presence/absence part of the type system. C# can do the same with libraries or simple types:

- Libraries: **RustyOptions**, **LanguageExt**, **OneOf**, or a lightweight custom `Result<T>` / `Option<T>`.
- Benefits: Forces callers to handle the error case, eliminates many null-reference and unexpected-exception bugs, and makes APIs self-documenting.

Example style (using a simple Result):
```csharp
public readonly record struct Result<T>
{
    public T? Value { get; }
    public string? Error { get; }
    public bool IsSuccess => Error is null;

    public static Result<T> Ok(T value) => new() { Value = value };
    public static Result<T> Fail(string error) => new() { Error = error };
}

// Usage with pattern matching
var result = GetUser(id);
string message = result switch
{
    { IsSuccess: true, Value: var user } => $"Found {user.Name}",
    { Error: var err } => $"Failed: {err}"
};
```

This mirrors Rust’s `match` + `?` operator ergonomics more closely than try/catch + null checks.

#### Algebraic Data Types + Exhaustive Pattern Matching
Rust enums can carry data and the compiler enforces exhaustive matching. C# records + switch expressions get you most of the way there (especially with C# 11+ list patterns and recursive patterns). Prefer sealed hierarchies or discriminated-union-style records over deep inheritance trees.

#### Ownership / Lifetime Thinking (even with a GC)
Rust’s ownership model (one owner, borrowing rules) teaches clearer resource and data-flow discipline:

- Prefer immutable data and pure functions.
- Use `readonly` / `init` / records aggressively.
- Treat `IDisposable` more carefully (RAII-like `using` scopes map reasonably to Rust’s `Drop`).
- Avoid unnecessary cloning/copying; pass by reference (`in`, `ref readonly`, `Span<T>`, `ReadOnlySpan<T>`) when possible.
- C# already has limited “borrow-checker-like” analysis for `ref`/`in` locals and parameters (especially with `ref struct`s and spans). Studying Rust makes these features more intuitive.

#### Composition over Inheritance + Traits-like Design
Rust prefers traits + composition. In C# this translates to:
- Prefer interfaces (especially with default interface methods) and composition.
- Use extension methods / extension traits sparingly for cross-cutting behavior.
- Favor small, focused types over large class hierarchies.

#### Immutability by Default
Rust variables are immutable unless marked `mut`. In C#:
- Prefer `readonly` fields, `init` properties, and records.
- Use `ImmutableArray`, `ImmutableList`, etc., or `ReadOnlySpan` for performance-critical paths.

#### Fearless Concurrency Patterns
Rust’s ownership + `Send`/`Sync` traits prevent data races at compile time. In C# you can approximate the discipline:
- Prefer message-passing / channels over shared mutable state.
- When sharing is needed, use clear ownership of locks (`Mutex`, `ReaderWriterLockSlim`, concurrent collections) and document who owns the data.
- `ref struct`s + spans help keep short-lived data off the heap and reduce GC pressure.

### 2. Actually Using Rust Code from C# (Interop)

When you need maximum performance, zero-cost abstractions, or memory safety guarantees that are hard to get in managed code, write the critical parts in Rust and call them from C#.

**Common approach:**
1. Build a Rust `cdylib` (or `staticlib`) with `#[no_mangle] pub extern "C"` functions.
2. Use `#[repr(C)]` on structs you want to share.
3. Call from C# with `LibraryImport` (preferred, source-generated) or classic `DllImport` / P/Invoke.
4. Tools that help:
   - Manual bindings (most common)
   - UniFFI + uniffi-bindgen-cs
   - csharp_binder and similar binding generators
   - `LibraryImport` source generator in modern .NET

**Typical use cases where this shines:**
- CPU-heavy algorithms, parsers, compression, cryptography, image/audio processing
- Systems-level code that needs deterministic resource management
- Reusing existing high-quality Rust crates (e.g., in security, networking, or data processing)

**Safety notes for interop:**
- Never let a Rust panic cross the FFI boundary (use `catch_unwind` or design APIs that return error codes/Results).
- Match memory ownership carefully (who frees what).
- Prefer simple C ABI types; complex ownership is better kept entirely on one side.

| Rust Feature              | Practical C# Equivalent / Benefit                          | When to Use |
|---------------------------|------------------------------------------------------------|-------------|
| `Result` / `Option`       | Result/Option types + pattern matching                     | Almost always for new APIs |
| Exhaustive matching       | Switch expressions + sealed hierarchies                    | Domain modeling |

### 1. Ownership & Move Semantics (Very Close Already)
Rust’s ownership model is essentially a stricter, compiler-enforced version of what good C++ already does with RAII + move semantics.

**Use in C++:**

- Lean heavily on move semantics (`std::move`, move constructors/assignment) instead of copying.
- Treat “moved-from” objects carefully — the C++ standard leaves them in a valid but unspecified state; Rust makes the original unusable.

**Practical tip:** Follow the C++ Core Guidelines (especially the resource-management and ownership sections). Many of them feel very “Rusty.”

### 2. Borrowing / Const Correctness / References
Rust’s borrow checker is stricter, but C++ already has the building blocks:

- Prefer `const` references and `const` member functions by default.
- Use `std::string_view`, `std::span` (C++20), and `std::mdspan` for non-owning views (very close to Rust slices/`&[T]`).
- Pass by `const&` or by value + move when you need to take ownership.
- Experimental / research efforts exist for actual borrow checking in C++ (some clang-based tools and proposals inspired by Rust).

### 3. Explicit Error Handling (`Result` / `Option`)
This is one of the highest-value imports from Rust.

**Modern C++ equivalents:**
- `std::optional` (C++17) ≈ `Option<T>`
- `std::expected` (C++23) ≈ `Result<T, E>`
- Older alternatives: Boost.Outcome, `tl::expected`, or a simple custom `Result` type.

Prefer returning `std::expected` or `std::optional` over throwing exceptions for recoverable errors. Combine with C++23’s improved pattern matching / monadic operations (`and_then`, `transform`, `or_else`, etc.) for a very Rust-like style.

### 4. Algebraic Data Types (Sum Types)
- Use `std::variant` + `std::visit` (or `std::visit` with overloaded lambdas).
- C++23 and later continue improving pattern matching, making this feel closer to Rust’s `match`.
- Libraries such as Boost.Variant2 or frozen can help for more ergonomic sum types.

### 5. Concepts ≈ Traits
C++20 **Concepts** are the closest thing C++ has to Rust traits for constraining generics. They give you much clearer error messages and more expressive generic code — very much in the spirit of Rust’s trait bounds.

### 6. Immutability by Default & Fearless Concurrency Discipline
- Make variables `const` whenever possible.
- Prefer immutable data structures or clear ownership of mutable state.
- For concurrency: treat mutexes as owning the data they protect (a common Rust idiom). Use channels (e.g., via libraries) more often than shared mutable state. Atomically shared data should be rare and carefully documented.

### 7. Zero-Cost Abstractions & Iterators
Both languages share this philosophy. C++ ranges (C++20) + views are quite comparable to Rust’s iterator adaptors, though the syntax is different.

### 8. Tooling Inspiration
- **Clippy** → `clang-tidy` + C++ Core Guidelines checks
- **rustfmt** → `clang-format`
- Strong static analysis and sanitizers (ASan, TSan, UBSan, MSan) become even more valuable when you adopt a more Rust-like strict style.

### Actual Interop (Calling Rust from C++)
This is often cleaner than C# interop:

- Expose a C ABI from Rust (`extern "C"`, `#[no_mangle]`, `#[repr(C)]`).
- Call it from C++ exactly like any other C library.
- You can also go the other direction (call C++ from Rust) with care around name mangling, exceptions, and object lifetimes.

Many high-performance or safety-critical projects already mix the two this way.

**Yes — even in plain C you can usefully adopt several of Rust’s core ideas**, though they become *conventions and disciplined patterns* rather than compiler-enforced language features.

Here’s what transfers well to ISO C (C11/C17/C23):

### 1. Clear Ownership Discipline
Rust’s biggest contribution is making ownership explicit. In C you do this by convention:

- Document (and name) who owns each piece of memory.
- Functions that *take ownership* should be clearly marked (e.g. `foo_take()`, or comments like `/* takes ownership of ptr */`).
- Functions that only borrow should take `const` pointers and document the expected lifetime.
- Prefer returning newly allocated objects and letting the caller free them, or use out-parameters with clear ownership transfer.

This is essentially what the best C codebases (Linux kernel, PostgreSQL, SQLite, etc.) already do — Rust just forces it.

### 2. Result / Option Style Error Handling
Very natural in C:

- Return error codes (`int`, or better a dedicated `enum` or `typedef`).
- Use out-parameters for the successful value.
- Or create simple tagged-union “Result” types:

```c
typedef struct {
    bool ok;
    union {
        int value;
        const char *error;
    } data;
} ResultInt;
```

Many high-quality C projects already use this style (or the classic `-1` + `errno`, or `NULL` + error string). Making it systematic and consistent is the Rust-inspired improvement.

### 3. Discriminated Unions (Sum Types)
C can model Rust-style enums carrying data with a struct + enum tag:

```c
typedef enum { SHAPE_CIRCLE, SHAPE_RECTANGLE } ShapeKind;

typedef struct {
    ShapeKind kind;
    union {
        struct { double radius; } circle;
        struct { double width, height; } rectangle;
    } data;
} Shape;
```

This is the classic “tagged union” pattern and is the closest thing C has to Rust enums. Used carefully, it gives you a lot of the same expressiveness.

### 4. Aggressive `const` Correctness (Immutability by Default)
- Mark everything `const` that can be.
- Prefer `const T *` for read-only access (shared borrow).
- Use `const` on local variables when they don’t need to change.

This is free in C and catches a surprising number of bugs.

### 5. Non-Owning Views / Borrowing
- Pass `(pointer, length)` pairs instead of relying on null-terminated strings when possible (`str` + `size_t`).
- Document lifetime expectations clearly (“the returned pointer is valid as long as `buf` lives”).
- Avoid storing raw pointers into data structures unless the lifetime relationship is obvious and stable.

### 6. Resource Management Patterns (Manual RAII)
C has no destructors, but you can still get many of the benefits:

- Consistent `foo_create()` / `foo_destroy()` pairs.
- `goto cleanup;` pattern (widely used in the Linux kernel and other serious C code) for centralized cleanup.
- Careful use of macros or inline functions to reduce boilerplate.

### 7. Fearless Concurrency Discipline
- Make data ownership extremely clear when crossing threads.
- Prefer message passing (queues) over shared mutable state.
- When sharing is required, document exactly which mutex protects which data.
- Treat “who owns this memory” as the central question, just like Rust does.

### 8. Actual Interop with Rust
This is one of the *easiest* directions:

- Rust can expose a pure C ABI (`extern "C"`, `#[no_mangle]`, `#[repr(C)]`).
- From plain C you just call it like any other C library.
- You get Rust’s safety and performance for the hard parts while keeping the rest of the program in C.

### What You *Don’t* Get
- Compile-time enforcement of ownership/borrowing rules
- Automatic destruction
- Fearless concurrency guarantees from the type system
- Algebraic data types with exhaustive matching enforced by the compiler
- Zero-cost move semantics (you still manage everything manually)

### Practical Recommendations for C
- Study high-quality C codebases that already practice strict ownership (Linux kernel, SQLite, Redis, PostgreSQL).
- Use static analyzers aggressively (clang-tidy, Coverity, CodeQL, Infer, etc.).
- Turn on every reasonable compiler warning and treat them as errors.
- Consider coding standards that push in a Rust-like direction (CERT C, MISRA, or project-specific rules about ownership and const).

**Bottom line for plain C:**  
You can’t get the compiler to enforce Rust’s rules, but you *can* adopt the same mental model — explicit ownership, systematic error handling via Result-like types, tagged unions, aggressive const, and clear lifetime documentation. Doing so makes C code significantly safer and easier to reason about.

**Safe and efficient `async`/`await` in C#** is one of the highest-leverage areas to get right. Here’s a focused, practical guide that aligns with the principles in the `rust-rules-for-csharp` skill (explicitness, clear ownership, minimal shared mutable state, and simplicity).

### 1. Core Safety Rules

| Rule | Why it matters | What to do |
|------|----------------|----------|
| **Never block on async code** | Deadlocks (especially in UI/ASP.NET classic sync context) and thread-pool starvation | Avoid `.Result`, `.Wait()`, `.GetAwaiter().GetResult()` in application code |
| **Async all the way** | Mixing sync and async creates hidden blocking | If a method is async, its callers should normally be async too |
| **Prefer `async Task` over `async void`** | `async void` is for event handlers only; exceptions become unobserved | Use `async Task` or `async ValueTask` everywhere else |
| **Handle exceptions** | Unobserved exceptions can crash the process or be swallowed | Always await tasks you care about, or observe them with continuation / `IAsyncEnumerable` patterns |
| **Respect cancellation** | Prevents wasted work and resource leaks | Accept `CancellationToken` and pass it downward |

### 2. Efficiency Rules

- **Use `ValueTask` / `ValueTask<T>`** when many calls complete synchronously (reduces allocations).
- **Avoid unnecessary `Task.Run`** — it only helps for CPU-bound work. I/O-bound code should just be async.
- **Configure awaits**: use `.ConfigureAwait(false)` in library/infrastructure code to avoid capturing the synchronization context. In application-level code (UI, ASP.NET request context) you often want the opposite.
- **Don’t create async state machines for trivial methods** — if a method just returns a completed task or forwards another task, consider returning the task directly.
- **Pool resources** (HttpClient, channels, buffers) rather than creating them per operation.
- Prefer `IAsyncEnumerable<T>` + `await foreach` for streaming data instead of loading everything into a list.

### 3. Recommended Patterns

**Good – async all the way + cancellation**
```csharp
public async Task<Result<User>> GetUserAsync(UserId id, CancellationToken ct = default)
{
    if (id.Value <= 0)
        return Result<User>.Fail("Invalid id");

    var user = await _db.Users
        .AsNoTracking()
        .FirstOrDefaultAsync(u => u.Id == id.Value, ct);

    return user is null
        ? Result<User>.Fail("Not found")
        : Result<User>.Ok(user);
}
```

**Good – ValueTask for hot paths**
```csharp
public ValueTask<int> GetCachedCountAsync()
{
    if (_cache.TryGetValue(out int count))
        return new ValueTask<int>(count);   // sync path, no allocation

    return new ValueTask<int>(LoadCountAsync());
}
```

**Good – safe fire-and-forget (when you truly need it)**
```csharp
_ = Task.Run(async () =>
{
    try
    {
        await DoBackgroundWorkAsync();
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Background work failed");
    }
});
```

**Avoid**
```csharp
// Deadlock risk + thread-pool abuse
var result = GetUserAsync(id).Result;

// Unobserved exception risk
async void OnButtonClick(...) { await SomethingAsync(); }
```

### 4. Concurrency & Shared State (ties into the skill)

- Prefer **message-passing** (`Channel<T>`, actors/Orleans) over shared mutable state.
- If you must share state, protect it with clear ownership (private data + lock, or concurrent collections).
- Treat `CancellationToken` as part of the ownership/lifetime story — when the token fires, stop work and release resources promptly.

- [ ] No `.Result` / `.Wait()` in async call chains

**Goose** (https://github.com/aardappel/goose) is a new memory-safe systems language by Wouter van Oortmerssen. Its defining idea is radical: **there is no heap**.

Every dynamic value lives on compiler-managed data stacks (bump-pointer style). Growth is just advancing a pointer, freeing is a single store to the stack top, and the type system keeps references safe without lifetime annotations.

### Standout ideas in Goose

| Idea | What Goose does | Practical takeaway |
|------|------------------|--------------------|
| **No heap** | Everything lives on a few compiler-assigned data stacks | Extreme control over allocation & locality |
| **Stable references on growth** | References into a growing array stay valid | Avoids the classic “iterator/reference invalidation” problem |
| **Inline nested data** | Variable-size fields and arrays stored contiguously, no pointers | Much better cache behavior and far fewer allocations |
| **Variable-size ADTs/enums** | Each variant occupies only the space it needs | More compact than classic tagged unions |
| **Relative (offset) references** | Narrow offsets instead of full pointers → position-independent data | Excellent for serialization / memory-mapping |
| **Share-nothing threads** | Threads have completely separate memory; communicate via typed queues + memcpy | Makes data races impossible by construction |
| **Multi-level returns** | Can return from several stack frames up without exceptions or `Result` plumbing | Simpler error propagation in some cases |
| **Zero lifetime annotations** | Compiler infers reference roots and rejects unsafe ones | Safety without the annotation burden of Rust |

Benchmarks claimed in the repo (as of late 2026) show Goose often faster than both idiomatic C++ and safe Rust while using less memory, largely because of the data layout and allocation model.

### What can we usefully borrow for C#?

You cannot eliminate the heap or the GC in C#, but several of Goose’s *design pressures* are still valuable and fit well with the existing skill:

1. **Prefer flat, contiguous, cache-friendly layouts**  
   Favor structs, arrays, `Span<T>`, and object pools over deep pointer-chasing object graphs when performance matters.

2. **Minimize allocations and prefer reuse**  
   Stack allocation, `ArrayPool`, slab/arena-style allocators, and recycling buffers become even more attractive once you’ve seen a language that has no heap at all.

3. **Stable indices / references into growable collections**  
   Prefer indices or carefully managed handles over holding long-lived references into collections that may resize.

4. **Inline nested data where it makes sense**  
   Design records/structs so related data lives together instead of being scattered across many small objects.

5. **Share-nothing + message-passing concurrency** (already partially in the skill)  
   Goose pushes this to the extreme. Reinforces the existing preference for `Channel<T>`, actors, and immutable messages.

6. **Compact representations of sum types**  
   When modeling discriminated unions, think about space efficiency, not just expressiveness.

7. **Position-independent / easily serializable structures**  
   Useful inspiration for high-performance serialization, memory-mapped files, or network protocols.

### Recommendation for the skill

The most actionable items to add to `rust-rules-for-csharp` are:

- Stronger guidance toward **flat, allocation-conscious data layouts**
- Preference for **indices/handles over long-lived object references** into growable collections
- Reinforced **share-nothing / message-passing** concurrency
- A note on **compact ADT / union representations**
